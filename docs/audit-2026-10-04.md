# Landscape 代码与开发流程审计

审计日期：2026-10-04（Asia/Shanghai）。

后续迁移进展：本地 custom 已迁入上游 0.25.2，修复与最终本地验证见文末。原始发现保留为审计基线；远端推送、分支保护与归档尚待具体 fork 上传授权，不能把本地修复当作远端已生效。

## 结论与范围

项目已有合理的 Rust workspace 分层、OpenAPI 类型生成、前端测试及 Linux CI 基础，但开发分支迁移尚未闭环，质量检查与实际发布路径脱节。当前不宜把“发布构建成功”当作代码质量合格。

本次为全仓结构与流程扫描，加关键路径代码审阅，不是对全部 1360 个受版本控制文件逐行证明正确。重点覆盖 HTTP 鉴权、插件生命周期、前端请求状态、DNS 连接、网关选择、迁移及构建发布。未实施生产网络/eBPF 数据面测试、漏洞库扫描或负载测试。

## 优先处理的问题

### F1 · P1 · 改密码不能撤销已有登录凭证

位置：`landscape-webserver/src/system/auth_config.rs:57`、`landscape-webserver/src/auth/mod.rs:74,111`。本地新后端分支同样存在。

改密码只更新密码配置。JWT 仅含 `sub` 和 `exp`，验证时仍只比对用户名；签名密钥也没有轮换。旧 token 在改密码后继续可用，且接近到期时还可以通过认证请求换取新 token。泄露凭证的持有者可持续续期，不能依赖改密码收回访问权限。

建议：引入可撤销的登录会话版本，在改密码时递增并在所有 HTTP、WebSocket、插件 cookie 鉴权入口检查。长期系统 token 应单独定义撤销策略。补充“改密码后旧 token 被拒绝且不能刷新”的测试。

### F2 · P1 · 实际发布分支没有质量门禁，GitHub 也没有保护规则

位置：`.github/workflows/check.yml:3`、`.github/workflows/build-and-release.yml:3,159`。

GitHub 实时查询：fork 的全部 10 个分支 `protected=false`，repository rulesets 为 `[]`。查询 fork 全部状态 PR 返回 `[]`；这不代表上游仓库没有 PR。

远端实际发布的是旧 `feature/extensions`：每次 push 触发构建和发布，但 Code Quality Check 只覆盖 main/dev 的 push 和目标为 main/dev 的 PR。发布 job 只依赖构建，不依赖检查或回归测试。最近 12 次运行均为 build and release，其中 3 次失败；成功的构建不能证明测试通过。

建议：对实际集成分支与所有 PR 启用检查；要求必要检查通过，禁止强推和删除。个人项目可以不强制第二位审核人，但应要求 PR 与 CI。发布使用明确版本 tag 或手动提升，并绑定同一提交的已通过检查。

### F3 · P1 · 新分支 Bun 迁移只完成了依赖配置，CI 和脚本仍用 pnpm

对象：本地 `feature/extensions@40d8f6fc`。

根 `package.json:7` 已是 `bun@1.4.2`，存在 `bun.lock`，不存在 `pnpm-lock.yaml`；但 `.github/workflows/check.yml:134-147` 仍 setup pnpm、缓存 pnpm 并执行 `pnpm install --frozen-lockfile`。发布 workflow、`web.sh`、`gen_ts_bindings.sh`、`scripts/pnpm_cmd.sh` 和 CONTRIBUTING 仍沿用 pnpm。

这使干净 CI 安装与仓库声明不一致，冻结 pnpm 安装缺少所需锁文件。本机已有 node_modules 能构建，不能覆盖此问题。

建议：一次性统一 CI、生成脚本、开发入口、构建入口、文档到 Bun，并用干净 checkout 的冻结安装验证。明确 Mac 前端与 Ubuntu Rust 的执行边界；当前 `gen_ts_bindings.sh` 会直接执行 cargo，不能作为 Mac 通用入口。

### F4 · P2 · 配置保存没有操作级互斥，固定临时文件可被并发覆盖

位置：`landscape-webserver/src/plugins/mod.rs:1190-1228`。本地新后端分支同样存在。

同一插件的请求共用 `<filename>.new` 和 `effective.new`。两个保存请求交错时，A 检验的文件可能已被 B 覆盖；随后 rename 可能提交另一请求的内容，或因文件已被移走而失败。HashMap 自身的锁没有覆盖完整保存事务；watchdog 的启动也可能与停机、替换配置交错。

建议：首先对同一插件的保存/启动/停止/卸载串行化；用独立临时文件，并明确失败恢复顺序。补充并发保存与 watchdog 交错测试。

### F5 · P2 · 保存配置后重启失败，接口仍返回成功

位置：`landscape-webserver/src/plugins/mod.rs:1221-1234`。本地新后端分支同样存在。

原服务先停止，再替换配置；`start_service` 失败只写 warning，随后返回 `Ok(())`。用户得到成功反馈，实际服务可能停机，旧配置也没有恢复。两次 rename 之间失败还可能留下不一致的配置状态。

建议：显式返回“已保存但启动失败”的错误/状态，或回滚配置并恢复旧服务；验证故障路径，不能只验证 YAML 合法性。

### F6 · P2 · 缺少可执行文件的插件包会留下无法正常重试的安装残留

位置：`landscape-webserver/src/plugins/mod.rs:1025-1035,1069`。本地新后端分支同样存在。

归档先 rename 为正式 package 目录，之后 `set_executable(...)?` 才检查可执行文件。包内缺少该文件时立即返回，尚未进入 install 的回滚分支，也没有注册 manifest。再次导入会报 already installed，正常删除接口又会因内存中没有插件而报 not found。

建议：在 staging 内完成文件存在性检查和权限设置，确认成功后再提交；所有提交后的错误统一清理。

### F7 · P2 · 日志接口读取全文件，截取尾部不能限制内存消耗

位置：`landscape-webserver/src/plugins/mod.rs:698-702,1126-1133`。本地新后端分支同样存在。

服务日志持续 append；读取接口先 `fs::read` 全文件再取末尾 64 KiB。长期运行后，大日志或并发请求会放大内存和磁盘压力。该模块没有轮转实现；外部是否另有轮转未核实。

建议：seek 到文件尾部读取有界字节，并配置日志轮转/大小上限。读取错误不应伪装成空日志。

### F8 · P2 · 前端测试实际失败，而且没有接入 PR 门禁

位置：`landscape-webui/src/test/visual_contract.test.ts:57`。

本次 `bun run test`：33 个文件中 32 通过、1 失败；165 个测试中 164 通过、1 失败。报告违规项为 CodeEditor.vue 的直接颜色和固定圆角，以及 CodeViewer.vue 的直接颜色。

当前前端 CI 仅检查格式，不执行 vitest 或类型检查/构建；新后端分支虽增加 common 单测和 config CLI E2E，也没有覆盖插件回归及前端测试。

建议：先判断这些颜色属于需要主题化的界面样式，还是有意保留的代码高亮色，再修正实现或精确限定规则。将测试、类型检查和构建纳入 CI。

### F9 · P2 · API bindings 的 “if-stale” 实际只检查文件是否存在

位置：`gen_ts_bindings.sh:15-21`。本地新后端分支仍相同。

只要 OpenAPI 文件、schema index 和 `.bindings.lock` 存在就跳过，不比较后端输入或内容 hash。切分支、改 schema 后可能继续使用旧类型，本地构建成功也可能只证明旧 API 自洽。

建议：先采用总是生成的简单正确流程；如耗时确实不可接受，再使用包含生成器配置与后端输入的指纹。CI 应从同一提交导出 OpenAPI 并生成前端。

## 分支与工作树判断

上游同步分支 + 独立功能分支的方向合理；本地新 `feature/extensions` 基于所保存的 origin/dev，只有 3 个额外提交，说明已尝试收敛旧扩展改动。

但目前存在三种容易混淆的状态：

- 当前目录还是 legacy；远端 `feature/extensions` 还是旧发布历史；本地同名 `feature/extensions` 已是新 dev 基线。两者按已核实的远端提交计算各有 82/18 个独有提交，不能当作普通 fast-forward 更新。
- 本地 `feature/extensions` 与 `feature/extensions-webui` 各有 3/2 个独有提交，不是简单的父子分支；共同修复（例如 Bun）已经出现独立提交，需要明确后续同步方式。
- `feat/geo-lookup`、`feat/http2-compression`、`feat/resource-names`、`feat/runtime-addresses`、`feat/theme-config` 都追踪 `origin/main`，而不是各自 fork 功能分支。默认 simple push 通常会因分支名不符拒绝，pull 却会合入上游 main；没有显式 pushRemote/remote.pushDefault。这里是误操作风险，并非断言会直接覆盖上游 main。

此外，7 个 worktree 条目已标记 prunable；新后端/前端分支没有 upstream；AGENTS.md 在当前目录未跟踪，新后端树也未收录它，因此新 clone 不会得到这些执行约束。

建议采用最小分支规则：

| 分支用途 | 建议规则 |
| --- | --- |
| fork/main | 保持上游稳定镜像，受保护 |
| 一个正式扩展集成分支 | 明确以哪个上游 dev 提交为基线，所有修改经 PR 与 CI |
| 短期功能分支 | 从集成分支创建，追踪 fork 同名远端分支 |
| 独立 UI 分支（若确需独立发布） | 声明后端兼容版本/capabilities，并增加组合验证 |
| legacy | 保留只读归档，不继续日常开发 |

不要直接强推新本地同名分支覆盖旧远端。先以不同远端分支名提交新历史，比较功能、迁移、产物与回滚方案，再决定替换策略。确认没有未保存工作后再清理失效 worktree 记录。

## 发布和可维护性补充

- 旧发布流程把 `0.24.3-extension.N` 标记 `prerelease: false`、`make_latest: true`，开发 push 即成为 Latest。若扩展系列本就被定义为稳定版，这可以是产品决策，但应有明确晋级门禁；目前没有。
- 本地新后端发布触发器已改成 tags/build，与远端旧发布机制不同，发布文档需要指定哪套生效。
- 工具链使用浮动 stable/nightly，第三方构建镜像/工具下载也没有全部固定摘要。建议在流程修复后固定已验证版本及 `--locked`，作为可复现性改进，不把它误报成已发现的依赖漏洞。
- 插件模块约 2200 行同时处理归档、进程、网络、配置与 HTTP。应先修事务边界，再按现有职责拆分少量模块；不建议引入新插件框架。
- NetworkSettings.vue 约 1872 行，Plugins.vue 约 917 行。可按已有功能面板拆分，但文件长度本身不是正确性缺陷。
- 项目已有路径遍历拒绝、归档文件类型/大小限制、接口鉴权、前端过期响应防护和网络协议测试，这些基础值得保留。此次没有因看到 unwrap 就直接判定漏洞。

## 建议执行顺序

1. 确定唯一开发/发布基线，保持 legacy 可回退；统一 Bun 和 Ubuntu Rust 入口。
2. 让 PR CI 覆盖实际分支并运行已有测试，修复现有失败；启用必要分支保护。
3. 修复会话撤销、插件安装回滚、配置并发与失败反馈、日志有界读取，并各加针对性回归检查。
4. 明确版本发布与回滚、API 生成契约；最后处理大文件拆分与工作树清理。
